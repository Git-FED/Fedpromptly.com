FedPromptly Roadmap

This roadmap is a directional map of the ecosystem, not a promise that every item will ship on a particular date. A roadmap item becomes active only when it has an owner, a problem statement, a smallest useful slice, and a public status.

Now — Make the front door useful

  • Publish the promotional page and mission narrative.
  • Make the four paths obvious: Learn, Tools, Build, Support.
  • Maintain a small, honest project catalog.
  • Provide a working support route and a clear status page.
  • Add accessible docs and a low-resource fallback.

Done means: a first-time visitor can understand the project in 30 seconds and choose a real next action.

Next — Make building visible

  • Publish starter templates for websites, Python tools, AI experiments, automations, portfolios, and blogs.
  • Add build logs that show decisions, tradeoffs, and failures.
  • Launch a lightweight project submission workflow.
  • Host recurring Build Nights or an asynchronous equivalent.
  • Add builder profiles only when there is a real identity and moderation model.

Done means: someone can go from “I do not know what to build” to a starter project with an example and a next step.

Later — Make contribution durable

  • Add contributor onboarding and maintainer ownership.
  • Create a public changelog and release process.
  • Define verification based on proof, not popularity.
  • Explore marketplace or creator revenue models only after legal, tax, licensing, and payment review.

Future concepts

FedSense, FedAPK, FedNet, and FedOS are long-horizon concept areas. They are not current product availability claims. Each needs a written problem definition, threat model, technical owner, and evidence before being presented as more than a direction.

Change policy

When a roadmap item changes, update this file with what changed, why, and what evidence informed the decision. A changed roadmap is healthier than a silent promise.

Evidence behind priorities

The order is based on the first-visit problem: a stranger needs orientation before a marketplace, account system, or large product catalog can create value. The first release should therefore optimize for comprehension, a concrete first build, and trust.

What will not be rushed

Payment expansion, identity systems, reputation scores, creator payouts, and future infrastructure concepts will not be presented as finished merely because they sound impressive. Each requires a real user problem, an owner, abuse and failure handling, privacy boundaries, and a way to roll back or change direction.

Roadmap review questions

At each review, ask: What did visitors try to do? Where did they stop? Which project or document helped? What support questions repeated? What can be removed? What evidence justifies the next slice?
